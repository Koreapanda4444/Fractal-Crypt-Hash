# FCH 보안 분석

이 문서는 트리 인코딩 버전 2와 16라운드 FCH 압축 코어에 대해 현재까지
확인한 내용을 한곳에 정리한 보고서입니다. 어떤 근거가 있고 어디까지
검사했는지, 앞으로 무엇을 더 분석해야 하는지를 함께 기록합니다. 영문판은
[security_analysis.md](security_analysis.md)에서 볼 수 있습니다.

사양서에 정의된 고전 공격 기준 보안 목표는 다음과 같습니다.

| 변형 | 충돌 | 원상 | 제2원상 |
| ---- | ---- | ---- | ------- |
| FCH-256 | 2^128 | 2^256 | 2^256 |
| FCH-512 | 2^256 | 2^512 | 2^512 |

아래 결과는 고정된 범위에서 재현할 수 있는 테스트 결과입니다. 설계가
퇴행했거나 축소 라운드가 약한 경우를 찾는 데는 유용하지만, 목표 공격 비용을
증명하거나 독립적인 암호분석을 대신하지는 않습니다. 양자 공격의 쿼리 규모는
아래에서 별도로 다룹니다.

## 분석 범위

FCH는 공개된 비키 해시로 가정합니다. 공격자는 메시지를 자유롭게 고르고,
함수를 원하는 만큼 계산하며, 사양과 소스 코드를 모두 알고 있습니다. 결과는
`fch_spec.ko.md`에 적힌 512비트 상태, 16라운드 ARX 압축, 1,024바이트 고정
리프, 정규 이진 트리 인코딩 버전 2, 출력별 마무리 영역에 한정됩니다.

라운드, 상수, 영역, 레코드, 패딩, 리프 크기나 트리 스케줄이 바뀌면 이
문서의 결과도 다시 측정하고 검토해야 합니다.

## 현재 구조를 선택한 이유

| 구성요소 | 의도 |
| -------- | ---- |
| 512비트 내부 상태 | FCH-512의 충돌 목표보다 낮은 내부 상태 충돌 한계가 생기지 않도록 함 |
| 정식 16라운드 | 현재 분석 기준인 8라운드 위에 8라운드 여유를 둠 |
| 형식이 정해진 128바이트 레코드 | 헤더, 데이터, 자식 상태와 마무리 정보를 구분함 |
| 영역값과 플래그 | 리프, 노드, 루트 마무리와 두 출력 크기의 압축 문맥을 분리함 |
| 정규 이진 트리 | 같은 패딩 길이에 하나의 트리만 허용하고 내용 기반 분할을 없앰 |
| 위치·범위 필드 | 서브트리의 레벨, 리프 구간, 바이트 구간과 자식 순서를 묶음 |
| 길이를 포함한 패딩 | 메시지 경계를 구분하고 원래 비트 길이를 결과에 반영함 |

이 구조는 여러 형태의 모호성을 설계 단계에서 없앱니다. 다만 구조만으로
충돌·원상·제2원상 저항성이 성립하는 것은 아니며, 압축 코어와 전체 트리
모드에 대한 분석이 함께 필요합니다.

1라운드 결과는 숨기지 않고 약한 상태로 표시합니다. 테스트가 확산이 부족한
코어와 이후 라운드를 실제로 구별한다는 뜻입니다. 2라운드부터 변화율이 50%에
가까워졌다는 사실만으로 보안 여유가 증명되는 것은 아닙니다. 현재는 8라운드를
축소 라운드 분석 기준으로 두고, 정식 코어에서 8라운드를 더 사용합니다.

### 축소 라운드 trail 자동 탐색

`tools/fch_trail_search.py`는 두 개의 고정된 8비트 입력군을 검사합니다. 첫 번째는
메시지 워드 0의 최하위 바이트에 XOR 차분 `0x01`을 적용하고, 두 번째는 워드
15의 최상위 바이트에 `0x80`을 적용합니다. 각 입력군과 라운드 수마다 256개
바이트 값을 전부 계산해 가장 가벼운 512비트 출력 차분을 찾습니다. 또 0이 아닌
모든 입력 바이트 마스크와 각 출력 비트의 상관을 정확한 Walsh 변환으로
검사합니다.

| 라운드 | 워드 0 최소 가중치 | 워드 15 최소 가중치 | 워드 0 최대 상관 | 워드 15 최대 상관 |
| ------ | ------------------- | -------------------- | ----------------- | ------------------ |
| 1 | 178 | 4 | 100.00% | 100.00% |
| 2 | 232 | 222 | 28.13% | 37.50% |
| 3 | 226 | 217 | 29.69% | 31.25% |
| 4 | 231 | 223 | 30.47% | 29.69% |
| 5 | 227 | 227 | 27.34% | 29.69% |
| 6 | 233 | 234 | 26.56% | 28.13% |
| 7 | 231 | 229 | 26.56% | 28.91% |
| 8 | 224 | 223 | 28.13% | 29.69% |

같은 출력에 구조화된 다중 비트 마스크 896개도 적용합니다. 절반은 연속된
2·4·8비트 구간이고, 나머지는 겹치지 않는 2·4·8개 출력 워드에서 같은 위치의
비트를 고른 마스크입니다. 선형 검사는 각 출력 마스크의 패리티를 0이 아닌 입력
바이트 마스크 255개와 비교합니다. 차분 검사는 입력군마다 중복을 제거한 XOR 쌍
128개를 각 마스크에 투영해 가장 큰 버킷을 기록합니다. 아래 표는 라운드별로 두
입력군에서 나온 최댓값을 정리한 것입니다.

| 라운드 | 2비트 최대 버킷 | 4비트 최대 버킷 | 8비트 최대 버킷 | 다중 비트 최대 상관 |
| ------ | ---------------- | ---------------- | ---------------- | ------------------- |
| 1 | 100.00% | 100.00% | 100.00% | 100.00% |
| 2 | 69.53% | 32.81% | 6.25% | 33.59% |
| 3 | 40.63% | 16.41% | 4.69% | 29.69% |
| 4 | 38.28% | 15.63% | 4.69% | 30.47% |
| 5 | 41.41% | 14.84% | 3.91% | 28.91% |
| 6 | 39.06% | 17.97% | 4.69% | 30.47% |
| 7 | 37.50% | 14.06% | 4.69% | 30.47% |
| 8 | 38.28% | 14.06% | 3.91% | 27.34% |

2라운드에서는 한 입력군의 2비트 투영에 눈에 띄는 집중이 남았습니다. 3라운드
이후에는 검사한 투영 중 값이 하나로 고정된 경우가 없었습니다. 이 수치는 수백
개의 마스크를 검사한 뒤 고른 최댓값이므로, 미리 정한 무작위 버킷 하나의 기대
빈도와 그대로 비교할 수는 없습니다.

열여섯 번의 완전 탐색에서 출력 차분이 0인 쌍은 없었습니다. 2라운드부터는 출력
워드 여덟 개가 모두 활성화됐습니다. 1라운드에서는 약한 trail이 그대로
드러나므로 초기 확산을 보안 근거로 잘못 해석하는 것도 피할 수 있습니다.

실행할 때마다 구체 탐색기를 16라운드 Python 기준 구현과 먼저 비교합니다. 별도
구현은 같은 ARX 연산을 Z3의 64비트 비트벡터로 모델링하고, 각 탐색에서 나온 최소
가중치 입력을 다시 계산합니다. 두 모델의 결과가 다르면 CI가 실패합니다. 이
수치는 정해진 두 8비트 입력군과 구조화된 출력 마스크 안에서만 정확합니다. 더
넓은 입력 차분, 구조화되지 않았거나 가중치가 더 큰 출력 마스크, 임의의
8·16라운드 특성에 대한 한계를 뜻하지는 않습니다.

### 전체 상태 characteristic 탐색

`tools/fch_characteristic_search.py`는 구체 탐색 범위를 두 개의 8비트 입력군에서
1,024비트 메시지 블록의 모든 단일 비트 차분으로 넓힙니다. 1,024개 차분을
결정적으로 만든 기준 메시지 32개에 각각 적용하고, 1~8라운드가 끝날 때마다
1,024비트 작업 상태 전체의 차분을 기록합니다. 라운드마다 메시지 쌍 32,768개를
검사합니다.

여기서 정확한 characteristic은 1라운드부터 해당 라운드까지 이어지는 전체 작업
상태 차분의 순서입니다. 마지막 열은 한 입력 차분에서 32개 기준 메시지 중 가장
많이 반복된 정확한 경로의 개수입니다.

| 라운드 | 최소 상태 가중치 | 활성 상태 워드 | 최소 출력 가중치 | 활성 출력 워드 | 최대 동일 경로 수 |
| ------ | ---------------- | -------------- | ---------------- | -------------- | ----------------- |
| 1 | 4 | 4 | 4 | 4 | 20/32 |
| 2 | 357 | 16 | 223 | 8 | 1/32 |
| 3 | 449 | 16 | 245 | 8 | 1/32 |
| 4 | 445 | 16 | 233 | 8 | 1/32 |
| 5 | 443 | 16 | 225 | 8 | 1/32 |
| 6 | 445 | 16 | 245 | 8 | 1/32 |
| 7 | 445 | 16 | 249 | 8 | 1/32 |
| 8 | 446 | 16 | 252 | 8 | 1/32 |

1라운드에서는 일부 메시지 비트에 희소하고 결정적인 경로가 남아 있었습니다.
2라운드부터는 검사한 모든 쌍에서 작업 상태 워드 16개와 압축 출력 워드 8개가
모두 활성화됐습니다. 같은 입력 차분에 대해 완전히 같은 characteristic 접두사가
서로 다른 기준 메시지에서 나온 경우도 없었습니다.

탐색을 시작하기 전에 평가기를 16라운드 Python 기준 구현과 비교합니다. 이 결과는
단일 비트 입력 차분과 고정된 기준 메시지 32개를 대상으로 한 경험적 검사입니다.
임의로 고른 차분이나 가중치가 더 큰 characteristic의 확률·상한이 아니며,
solver 기반 탐색을 대신하지 않습니다. CI의 2라운드 이후 기준인 상태 256비트,
출력 128비트, 전체 워드 활성화와 동일 경로 없음은 보안 한계가 아니라 보수적인
회귀 감지선입니다.

### 회전쌍과 가산차분 검사

회전쌍 검사는 메시지의 모든 64비트 워드를 1·8·16·24·32·63비트만큼 돌린 뒤,
그 압축 결과를 원래 출력에 같은 회전을 적용한 값과 비교합니다. 라운드마다
3,072쌍을 검사했으며 정확한 회전 관계는 나오지 않았습니다. 모든 출력 워드가
활성화됐고 최소 거리는 210비트 이상이었으며, 회전별 평균이 50%에서 벗어난
최댓값은 0.21%였습니다.

가산차분 검사는 메시지 워드 0·5·10·15에 짧은 carry, 32비트 경계, 최상위 비트와
반복 바이트 carry를 확인하는 네 모듈러 차분을 적용합니다. 1라운드는 평균
20.74%, 최소 거리 14비트였고 일부 쌍은 출력 워드 네 개만 활성화돼 약점이
분명했습니다. 2라운드부터는 평균 49.93%~50.02%, 최소 거리 206비트 이상을
기록했고 모든 쌍에서 출력 워드 여덟 개가 활성화됐습니다. 출력 차분이 0인 쌍은
없었습니다.

이 검사는 고정된 IV, 영역값, 카운터와 플래그를 사용하는 실제 압축 문맥을
대상으로 합니다. 이런 상수도 단순한 워드 단위 회전 대칭을 깨는 데 영향을
줍니다. 따라서 내부 회전 characteristic, 더 깊은 관련 tweak 공격이나 검사하지
않은 고확률 가산 trail까지 없다는 뜻은 아닙니다.

### 차분 확률과 관련 문맥

경험적 확률 검사는 단일 비트 네 개와 이중 비트 네 개의 XOR 입력 차분을
사용합니다. 차분마다 4,096쌍을 만들고, 512비트 출력 차분을 고정된 16비트 투영
네 개로 나눠 빈도를 셉니다. 2·4·8·16라운드에서 가장 큰 버킷은 네 쌍으로
0.0977%였고, 1라운드는 세 쌍으로 0.0732%였습니다. 512비트 출력 차분이 0인
쌍은 없었습니다.

이 검사는 눈에 띄게 높은 차분 집중을 재현 가능하게 찾는 용도입니다. 512비트
전체 characteristic의 확률을 계산한 것이 아니며, 16비트 투영 결과만으로
검사하지 않은 전체 상태 trail의 상한을 제시할 수는 없습니다.

관련 문맥 검사는 같은 128바이트 블록에 대해 내부 압축 문맥 여덟 종류를
바꿉니다. 인접 카운터와 최상위 비트 카운터, 리프·노드·출력 영역과 플래그,
FCH-256·FCH-512 출력 문맥, 1비트 영역 차분과 복합 변화를 포함합니다. 1라운드는
평균 43.14%, 최소 거리 76비트, 최대 비트 편향 22.78%로 약했습니다. 2라운드부터
평균은 49.92%~49.99%, 최소 거리는 211비트 이상이었고 모든 출력 워드가
활성화됐으며 최대 비트 편향은 2.95% 이하였습니다. 같은 출력이 나온 관련 쌍은
없었습니다.

영역값, 카운터와 플래그는 공개 해시 API에서 공격자가 고르는 값이 아니라 유효한
FCH 인코딩이 정합니다. 이 검사는 내부 문맥 사이의 분리를 확인할 뿐, 관련 키
공격에 대한 증명이나 rebound·meet-in-the-middle 공격의 한계를 뜻하지 않습니다.

### Rebound와 meet-in-the-middle 탐색

축소 라운드 테스트 빌드에는 1,024비트 내부 작업 상태를 준비하고 정방향·역방향으로
라운드를 실행하는 기능을 넣었습니다. 전체 8라운드와 2라운드에서 시작하는
4라운드 구간을 왕복해 시작 상태로 정확히 돌아오는지 확인하며, 정방향 결과도
일반 압축 함수의 출력과 비교합니다. 이 기능은 `FCH_ENABLE_REDUCED_ROUND_TESTS`가
정의된 빌드에만 포함되므로 일반 해시 인터페이스에는 영향을 주지 않습니다.

Rebound형 검사는 블록의 첫 바이트와 마지막 바이트에 걸친 12비트 메시지 차분 중
0이 아닌 4,095개를 전부 확인합니다. 4라운드는 2+2, 8라운드는 4+4, 16라운드는
8+8로 나누고 1,024비트 전체 작업 상태의 차분을 측정했습니다. 중간 상태 최소
가중치는 373·455·460비트였고, 모든 중간·최종 상태에서 워드 16개가 활성화됐으며
256비트 이하의 중간 상태와 차분 0인 후보는 없었습니다. 최종 상태의 최소
가중치는 각각 455·460·462비트였습니다.

Meet-in-the-middle 검사는 의도적으로 작은 12비트 후보 공간에서 8라운드를 4+4로
나눕니다. 정방향 중간 상태 4,096개를 저장하고, 전체 내부 목표 상태에서 다른
후보 4,096개를 4라운드 역산합니다. 먼저 24비트 투영을 맞춘 다음 1,024비트
전체를 비교했으며, 투영 일치와 전체 일치는 각각 한 쌍이었습니다. 전체가 맞은
것은 심어 둔 후보 하나뿐이었습니다.

이 복구는 FCH 원상 공격이 아니라 구현과 탐색 모델의 일관성 검사입니다. 전체
내부 목표 상태와 메시지 비트 중 12비트를 제외한 나머지가 알려졌다고 가정합니다.
모든 라운드가 메시지 워드 16개를 전부 사용하므로 같은 후보를 앞뒤 양쪽에서
계산해야 하며, 독립적인 앞·뒤 변수 분할 없이 정방향 4,096회와 역방향 4,096회가
필요합니다. Rebound형 검사도 최적화된 inbound 해법이 아니라 정해진 차분군의
열거입니다.

### 출력 전용 공격 탐색

출력 전용 검사는 내부 상태를 안다는 가정을 제거합니다. 메시지의 정해진 두
바이트를 바꿔 16비트 공간 전체를 열거하며, 512비트 압축 출력만 관찰합니다.
후보 65,536개를 공간 안에서 심어 둔 표적과 세 번째 바이트도 다른 공간 밖 표적에
각각 비교합니다. 내부 표적은 탐색기가 정확한 일치를 복구하는지 확인하고, 외부
표적은 선언한 공간에 예상하지 못한 원상이 있는지 검사합니다.

모든 후보를 출력 앞 24비트로 묶은 뒤 각 그룹에서 512비트 전체 충돌도 확인합니다.
두 표적까지의 해밍 거리 역시 측정하지만, 1,024비트 작업 상태를 읽거나 복원하지
않습니다.

| 라운드 | 내부 표적 정확 일치 | 외부 표적 정확 일치 | 24비트 충돌 쌍 | 최대 버킷 | 완전 충돌 | 최소 표적 거리 |
| ------ | ------------------- | ------------------- | ------------- | --------- | --------- | -------------- |
| 4 | 1 | 0 | 129 | 2 | 0 | 207 |
| 8 | 1 | 0 | 143 | 2 | 0 | 201 |
| 16 | 1 | 0 | 104 | 2 | 0 | 207 |

내부 표적에서는 원래 후보 하나만 정확히 일치했습니다. 24비트 쌍은 출력을 짧게
잘라서 생기는 예상 가능한 충돌이며 512비트 전체 충돌로 이어지지 않았습니다.
이 결과는 고정된 16비트 입력군 안에서만 완전 탐색입니다. 전수조사보다 빠른
공격을 찾았다는 뜻이 아니며, 전체 입력 공간의 원상·충돌 비용이나 더 강한
rebound, meet-in-the-middle, splice, 출력 전용 공격의 한계를 제시하지 않습니다.

멀티콜리전 검사에서 나온 20비트 앞부분 일치는 의도적으로 결과를 짧게 잘랐기
때문에 생기는 예상 가능한 birthday 현상입니다. 그 쌍들이 512비트 전체 상태
충돌로 이어지지 않았다는 점을 확인한 것이며, 이 제한된 검사만으로
멀티콜리전 저항성이 증명되는 것은 아닙니다.

Expandable message 검사는 접두사와 마지막 2 KiB 접미사를 유지한 채 그 사이에
완전한 리프 1~4개를 삽입했습니다. 장·단문 96쌍 중 원시 루트나 해시값을 재사용한
쌍은 없었습니다. Herding 검사는 서로 다른 첫 리프 256개 뒤에 같은 3 KiB를
붙였습니다. 이번 실행에서는 20비트 루트 투영조차 겹치지 않았고, 전체 루트와
해시값도 수렴하지 않았습니다.

다중 표적 검사는 서로 독립적인 4 KiB 표적 64개와 변형 후보 256개를 모두
비교했습니다. 출력 크기마다 총 16,384회를 비교했으며 일치는 없었습니다. 이들은
입력과 범위가 고정된 결정적 탐색입니다. 압축 함수 충돌을 먼저 만들거나, bridge
블록을 최적화하거나, expandable message·diamond·herding·다중 표적 공격의
점근적 비용을 계산하지는 않습니다.

FCH-256과 FCH-512는 의도적으로 같은 트리 루트에서 출력 마무리를 시작합니다.
그 뒤 출력 크기와 영역값을 담은 출력 레코드가 두 변형을 나눕니다. 메시지 256개
모두에서 출력 전 루트는 같았지만 FCH-256 해시값이 FCH-512의 앞·뒤 256비트와
같아진 경우는 없었습니다. 최소 거리는 107비트와 106비트, 평균은 49.52%와
49.69%였습니다. 표본 안에서 구현된 영역 분리를 확인한 결과일 뿐, 두 변형 사이의
계산 재사용 공격이 불가능하다는 증명은 아닙니다.

## 조건부 트리 보안 논증

트리 모드는 역할이 구분된 세 함수로 나누어 생각할 수 있습니다.

- `Leaf(구조 정보, 데이터)`는 512비트 리프 상태를 만듭니다.
- `Node(구조 정보, 왼쪽 구조 정보와 상태, 오른쪽 구조 정보와 상태)`는 512비트 내부
  노드 상태를 만듭니다.
- `Output(변형, 루트 구조 정보와 상태, 원본 길이, 패딩 길이)`은 최종 해시값을
  만듭니다.

여기서 각 함수는 영역값, 플래그, 카운터와 마지막 레코드 표시까지 포함한 전체
레코드 처리 과정을 뜻합니다. FCH-256의 `Output`에는 256비트 절단이 포함되고,
FCH-512는 마무리된 상태 전체를 반환합니다.

다음 세 성질은 암호학적 가정이 아니라 현재 형식에서 바로 확인할 수 있습니다.

1. **패딩은 단사입니다.** 마지막 8바이트에 원본 비트 길이가 들어가고,
   그 앞의 `0x80`이 메시지와 0 채움 영역을 구분합니다. 따라서 유효한 두 패딩
   문자열이 같다면 원본 길이와 메시지도 같습니다.
2. **트리는 하나로 결정됩니다.** 패딩 길이가 리프 수를 정하고, `n`보다 작은
   가장 큰 2의 거듭제곱을 왼쪽 자식에 배정하는 규칙이 모든 분할을 재귀적으로
   정합니다. 따라서 리프 수에 대한 귀납으로 각 범위의 트리와 구조 정보가 하나로
   결정됩니다.
3. **레코드의 역할과 위치가 겹치지 않습니다.** 리프, 노드, 자식과 출력
   레코드는 서로 다른 태그, 영역값과 플래그를 사용합니다. 구조 정보는 레벨,
   리프 범위, 바이트 범위와 자식 번호를 포함하므로 순서 변경, 위치 이동이나
   재그룹화는 적어도 하나의 입력 필드를 바꿉니다.

이 세 항목은 인코딩 성질입니다. 서로 다른 레코드가 서로 다른 상태를 만든다고
가정하지는 않습니다. 그 부분은 별도로 분석해야 하는 암호학적 성질입니다.

### 충돌의 위치

서로 다른 메시지 `M`과 `M'`이 한 변형에서 같은 해시값을 만든다고 가정하고,
두 `Output` 함수에 들어가는 전체 입력을 비교합니다.

- 입력이 다르다면 그 쌍은 이미 최종 출력 함수에서의 충돌입니다. FCH-256에서는
  의도된 256비트 절단 때문에 생기는 충돌도 여기에 포함됩니다.
- 출력 입력이 같다면 두 루트 구조 정보와 루트 상태도 같습니다. 두 정규 트리를
  루트부터 아래로 비교했을 때 서로 다른 자식 묶음이 같은 부모 상태를 만들면
  `Node` 충돌입니다. 비교한 모든 노드 입력이 같다면 결국 처음으로 데이터가
  다른 리프에 도달합니다. 패딩의 단사성 때문에 이런 리프가 반드시 존재하며,
  두 리프 상태가 같다면 `Leaf` 충돌입니다.

따라서 다른 트리 모양, 자식 순서 변경, 서브트리 접합과 메시지 경계의 모호성만
이용해 같은 해시값을 얻을 수는 없습니다. 트리 해시의 충돌은 최종 출력 함수나
역할이 정해진 리프·노드 함수의 충돌로 귀결됩니다. 다만 이 결론은 각 함수가
해당 공격에 저항한다는 조건에 의존합니다.

### 제2원상의 위치

목표 메시지 `M`을 고정해도 같은 논리를 적용할 수 있습니다. 같은 해시값을 갖는
다른 `M'`은 최종 출력 함수의 제2원상이 되거나, 처음 갈라지는 리프 또는 노드에서
충돌을 일으켜야 합니다. 정규 스케줄 때문에 공격자가 목표 트리와 다른 파싱을
같은 계산인 것처럼 제시할 수는 없습니다.

이 논증만으로는 공격 비용이 나오지 않습니다. 다음 절에서는 명시적인 이상적 함수
모델 아래에서 보수적인 합집합 상한을 계산합니다. 실제 압축 구조가 그 모델을
만족한다는 증명은 아닙니다.

### 정량적 조건부 한계

길이가 `L`바이트인 메시지에 대해 다음 값을 정의합니다.

```text
P = max(64, L + 9)
N = ceil(P / 1024)
b = P - 1024(N - 1)
D = ceil(log2(N))
T = 2N - 1
```

`N`은 리프 수, `b`는 마지막 리프 길이, `D`는 루트 레벨입니다. `T`는 목표
트리에서 실행하는 리프와 내부 노드 함수의 전체 횟수입니다. 모든 내부 노드의
자식이 둘이므로 리프가 `N`개인 트리에는 내부 노드가 정확히 `N - 1`개 있습니다.

완성된 해시 하나가 압축 함수를 호출하는 정확한 횟수는 다음과 같습니다.

```text
C(L) = 13N - 11 + ceil(b / 120)
```

완전한 리프 하나는 헤더 1개와 데이터 레코드 9개를 사용합니다. 마지막 리프는
헤더 1개와 데이터 레코드 `ceil(b / 120)`개, 내부 노드는 각각 레코드 3개,
출력 마무리는 레코드 1개를 사용합니다.

조건부 모델에서는 서로 다른 정상 입력에 대한 `Leaf`와 `Node`를 서로 독립적인
512비트 무작위 함수로 취급합니다. `d`가 256 또는 512일 때 각 `Output` 변형도
독립적인 `d`비트 무작위 함수로 둡니다. 압축 구조 안에 지름길이 없다는 가정도
포함합니다. 영역값과 태그는 이런 분리를 의도하지만 증명하지는 않습니다.

공격자가 계산한 서로 다른 최종 출력 입력 수를 `H`, 서로 다른 `Leaf`와 `Node`
입력의 합을 `Q`라고 하겠습니다. 고정 표적에 이미 들어 있는 트리 상태는 `Q`에
포함하지 않습니다. 합집합 상한을 적용하면 다음과 같습니다. 오른쪽 값이 1보다
크면 1로 제한합니다.

```text
Adv_collision(H, Q) <= H(H - 1) / 2^(d + 1)
                       + Q(Q - 1) / 2^513

Adv_second-preimage(H, Q; T) <= H / 2^d + TQ / 2^512

Adv_preimage(H) <= H / 2^d
```

서로 다른 표적이 `r`개이고 그 트리에 들어 있는 리프·노드 상태의 합이
`T_total`이면 다중 표적 상한은 다음과 같습니다.

```text
Adv_multi-target(H, Q; r, T_total)
    <= rH / 2^d + T_total Q / 2^512
```

이 식에서 역할별 함수 계산 횟수를 기준으로 다음 규모를 얻습니다. 이상적 모델에서
필요한 규모일 뿐, 실제 공격을 구성했다는 뜻은 아닙니다.

- 해시값 충돌의 birthday 규모는 `H = 2^(d/2)` 부근입니다.
- 내부 상태 충돌의 birthday 규모는 `Q = 2^256` 부근입니다.
- 고정 표적의 제2원상은 출력 마무리를 통하면 `H = 2^d`, 목표 트리 상태를
  통하면 `Q = 2^512 / T` 정도가 필요합니다.
- 표적이 `r`개이면 각각 `2^d / r`와 `2^512 / T_total` 정도로 바뀝니다.

트리 크기는 메시지 질의 횟수와 전체 연산량에 서로 다르게 영향을 줍니다. 서로
독립적인 메시지 `q`개가 각각 최대 `T_max`개의 새 트리 함수 계산을 만든다면
`Q <= qT_max`입니다. 따라서 전체 메시지 질의는 대략 `2^256 / T_max`번 만에
birthday 규모에 도달할 수 있지만, 서브트리 재사용이 없다면 그 질의들이 실행한
트리 함수의 합은 여전히 약 `2^256`회입니다. 이 계산에서는 트리 때문에 일반적인
기초 연산량이 줄어들지 않습니다.

고정 표적에서는 표적이 맞춰 볼 상태 `T`개를 제공하므로 식이 달라집니다. 아래
표는 의도적으로 보수적인 `2^512 / T` 규모를 보여 줍니다. 위치와 범위 정보 때문에
특정 후보와 호환되지 않는 상태도 많을 수 있으므로 실제 비용은 표보다 클 수
있습니다.

| 원본 길이 `L` | 리프 `N` | 트리 상태 `T` | 압축 호출 `C(L)` | `log2(2^512 / T)` |
| ------------- | -------- | ------------- | ---------------- | ------------------ |
| 0바이트 | 1 | 1 | 3 | 512.00 |
| 1 KiB | 2 | 3 | 16 | 510.42 |
| 1 MiB | 1,025 | 2,049 | 13,315 | 501.00 |
| 1 GiB | 1,048,577 | 2,097,153 | 13,631,491 | 491.00 |
| `2^61 - 1`바이트 | `2^51 + 1` | `2^52 + 1` | 29,273,397,577,908,227 | 약 460.00 |

FCH-256은 형식상 허용되는 모든 길이에서 `2^256` 출력 마무리 항이 내부 목표 상태
항보다 작습니다. FCH-512는 이 보수적인 환원만으로 길이와 무관한 제2원상 수치를
보장할 수 없습니다. 형식상 최대 길이에서는 설명 가능한 규모가 역할별 함수 계산
약 `2^460`회까지 내려갑니다. 이것은 `2^460` 공격을 제시한 결과가 아니지만,
모든 메시지 길이에 `2^512`를 그대로 주장할 근거도 되지 않습니다.

반복형 Merkle-Damgard 해시에는 장문 제2원상 지름길이 알려져 있습니다. Kelsey와
Schneier의 [Second Preimages on n-bit Hash Functions for Much Less than 2^n
Work](https://www.schneier.com/wp-content/uploads/2016/02/paper-preimages.pdf)를
참고할 수 있습니다. 그 공격은 반복 체인 구조에 의존하므로 FCH의 위치 결합 정규
트리에 그대로 적용된다고 주장하지 않습니다. 여기서는 길이와 무관한 숫자 하나만
적는 대신 `T`에 대한 의존성을 밝혀야 하는 이유로 인용합니다.

### 논증의 경계

| 항목 | 현재 상태 |
| ---- | --------- |
| 패딩과 정규 트리의 유일성 | 형식으로 확인됨 |
| 다른 모양과 위치의 거부 | 형식과 구현 검사로 확인됨 |
| 해시 충돌·제2원상의 발생 위치 | 역할별 함수의 안전성을 조건으로 성립 |
| 영역값과 태그가 만드는 독립성 | 설계 가정이며 증명되지 않음 |
| 사양서의 수치 보안 목표 | 이상적 함수 모델 안에서만 일치하며 FCH-512의 길이 무관 제2원상 목표는 제외 |
| 장문·다중 표적 공격에서의 보안 손실 | 위에 매개변수별 합집합 상한을 제시했으며 엄밀성은 미확인 |

이 논증으로 남은 질문의 범위는 좁아집니다. 공격이 트리 표현의 모호성에만 기대기는
어렵지만, 압축 코어, 레코드 흡수 방식, 출력 절단이나 일반적인 트리 해시 공격을
이용할 가능성은 여전히 분석해야 합니다.

## 양자 보안 범위

이 절은 공격 모델과 일반적인 기준선을 정합니다. FCH의 양자 공격 저항성이
증명됐다는 뜻은 아닙니다.

### 모델과 비용 단위

FCH는 공개된 비키 해시로 둡니다. 공격자는 전체 해시 또는 필요한 경우 역할별
`Leaf`, `Node`, `Output` 함수를 가역 회로로 구현한 뒤 중첩 상태에서 질의할 수
있다고 가정합니다. 아래 수치는 양자 오라클 질의 횟수만 셉니다. 논리·물리 게이트,
회로 깊이, 큐비트, 양자 메모리, 오류 정정과 가역 FCH 회로를 만드는 비용은
포함하지 않습니다.

전체 해시 한 번의 질의도 내부에서는 메시지 길이에 따른 압축 호출을 가역적으로
실행하고 임시 상태를 되돌려야 합니다. 따라서 쿼리 모델에서 한 번으로 세더라도
실제 비용은 메시지 길이와 회로 구성에 따라 달라집니다. 아직 이 회로와 자원 비용을
계산한 결과는 없습니다.

일반 기준선에서는 역할별 함수를 서로 독립적인 무작위 함수로 취급합니다. 영역
태그는 이 분리를 의도하지만 모델을 증명하지는 않습니다. FCH에 대한 양자
랜덤 오라클 모델의 환원도 없고, ARX 코어나 트리 모드의 양자 구조 공격 분석도
아직 없습니다.

### 일반적인 양자 쿼리 규모

[Grover 탐색](https://arxiv.org/abs/quant-ph/9605043)은 구조가 없는 표적 탐색의
비용을 제곱근 수준으로 줄입니다. 따라서 `d`비트 이상적 출력의 일반 원상이나
하나로 고정된 최종 출력의 제2원상은 약 `2^(d/2)`번의 양자 질의가 필요합니다.

[Brassard-Høyer-Tapp 충돌
알고리즘](https://arxiv.org/abs/quant-ph/9705002)은 `d`비트 이상적 출력에서
일반 충돌의 쿼리 규모를 `2^(d/3)`으로 낮춥니다. 이 숫자만으로 전체 구현 비용을
알 수는 없습니다. 원래 알고리즘은 상당한 저장 공간을 사용하며 시간과 공간의
절충도 함께 제시합니다.

| 변형 | 일반 충돌 질의 | 일반 원상 질의 | 고정 표적 제2원상 질의 |
| ---- | -------------- | -------------- | ----------------------- |
| FCH-256 | 약 `2^85.33` | 약 `2^128` | 약 `2^128` |
| FCH-512 | 약 `2^170.67` | 약 `2^256` | `min(2^256, 2^256 / sqrt(T_compatible))` |

이 값은 이상적 함수의 쿼리 규모이지, 실제 공격 비용이나 보안 증명이 아닙니다.
512비트 내부 함수의 일반 충돌 규모도 약 `2^(512/3) = 2^170.67`번입니다.
따라서 FCH-256의 일반 양자 충돌 지수는 128비트가 아닙니다. 256비트 출력 때문에
약 85.33비트가 됩니다. 같은 모델에서 FCH-512의 일반 충돌 지수는 약
170.67비트입니다.

### 트리 표적과 긴 메시지

고정된 표적 메시지에 대해 `T_compatible`을 후보 입력의 역할, 위치, 범위와 나머지
구조 정보에 맞는 표적 상태 수로 정의합니다. 표적 트리의 리프·노드 상태 수는
`T = 2N - 1`이므로 `T_compatible <= T`입니다. 512비트 역할별 함수의 입력 중
이 상태 하나에 도달하는 값을 찾는 일반적인 규모는 다음과 같습니다.

```text
Q_tree_quantum(T_compatible) = 2^256 / sqrt(T_compatible)
```

최종 출력에서 직접 찾는 경로와 합치면 조건부 규모는 다음과 같습니다.

```text
Q_second-preimage(d, T_compatible)
    = min(2^(d/2), 2^256 / sqrt(T_compatible))
```

`T_compatible = T`를 넣으면 의도적으로 보수적인 낮은 규모를 얻습니다. 형식상
최대 길이에서는 `T = 2^52 + 1`이므로 내부 항이 역할별 함수 질의 약 `2^230`번이
됩니다. FCH-256은 여전히 약 `2^128`인 출력 탐색이 더 작습니다. FCH-512는 이
계산에서 `2^256`이 아니라 약 `2^230`까지 내려갑니다.

`2^230`은 실제 공격을 만들었다는 뜻이 아닙니다. 모든 표적 상태를 중첩 상태에서
찾을 수 있다고 가정하고, 구조 정보의 비호환성과 회로 비용을 무시한 값입니다.
이 보수적인 이상적 함수 계산으로 설명할 수 있는 가장 낮은 일반 규모만 표시합니다.
구조를 이용한 양자 공격은 이보다 쌀 수 있고, 실제 가역 구현은 훨씬 비쌀 수
있습니다.

서로 다른 표적 해시값이 `r`개이면 일반 출력 탐색은
`2^(d/2) / sqrt(r)`이 됩니다. 모든 표적 트리에 서로 다른 호환 내부 상태가
`T_total`개 있으면 역할별 함수 탐색은 `2^256 / sqrt(T_total)` 규모입니다.
이 식은 효율적인 중첩 멤버십 검사가 있다고 가정하며, 표적 집합이 더는 희소하지
않으면 가능한 전체 공간을 넘지 않도록 제한해야 합니다.

이 지수만으로 NIST 양자내성 등급을 붙이지 않습니다. 그런 분류에는 실제 게이트,
깊이, 메모리와 실패 비용뿐 아니라 블랙박스 쿼리 복잡도가 아닌 FCH 자체의 분석이
필요합니다.

## 구현 검증

분석 대상 알고리즘과 실제 코드가 어긋나지 않도록 다음 검사도 함께 실행합니다.

- 고정 벡터와 C/Python 기준 구현 비교 96건
- 8비트 축소 라운드 완전 탐색과 Z3 입력 재검증
- 경계값과 여러 청크 분할에서 원샷·스트리밍 결과 비교
- big-endian CI를 포함한 little-endian 직렬화 확인
- 메모리 할당, reader, 오버플로와 API 수명주기 실패 처리
- AddressSanitizer, UndefinedBehaviorSanitizer와 목적별 libFuzzer 스모크 대상 5개
- 소스·테스트 번역 단위 31개에 대해 경고를 오류로 처리하는 GCC 경로 기반
  정적 분석
- 8 MiB 입력의 제한 메모리 스트리밍
- CI에서 스케일링과 같은 길이 입력의 시간, 할당 횟수와 최대 힙 확인

이 검사를 통과했다는 것은 확인한 구현이 일관되게 동작했다는 뜻입니다. 구현
검사 범위가 넓다고 해서 암호학적 증명이 되는 것은 아닙니다.

35개에서 구조화 입력 140개를 실행합니다. 구조화 입력은 0, 1, 위치 기반 수열과
교대 패턴을 포함합니다. CI는 핵심 해시, 스트림 분할, 패딩 경계, 정규 트리 결합,
CLI 입력 처리를 각각 맡는 sanitizer 기반 libFuzzer 대상도 실행합니다. 각 대상은
서로 다른 고정 시드로 1,024회씩 실행하므로 총 요청 횟수는 5,120회입니다. 패딩
대상은 작은 제어 입력을 최대 16,385바이트의 메시지 길이로 변환해 최소 패딩과
트리 리프 경계 주변의 마커·길이 필드 전환을 직접 검사합니다.

GCC 경로 기반 분석은 이전에 라이브러리 소스 8개와 명령행 도구만 검사했습니다.
이제 벤치마크와 테스트 번역 단위 21개도 검사하며, 여기에는 전용 퍼즈 대상 4개와
필요한 빌드 플래그를 적용한 축소 라운드 테스트 2개가 포함됩니다. 범위를 넓히는
과정에서 분할 민감도 테스트의 할당 실패 경로에 누수가 하나 발견됐고, 반환 전에
성공한 할당을 해제하도록 고쳤습니다. 이 수정으로 라이브러리 코드는 바뀌지
않았습니다.

실행 시간 검사는 내용이 서로 다른 64 KiB 패턴 4개를 FCH-256·FCH-512의 원샷과
1 KiB 스트리밍 경로에서 해시합니다. 각 패턴은 해시 16회를 한 묶음으로 하여
순서를 섞은 7회 측정을 거칩니다. 같은 길이의 모든 패턴에서 할당 횟수와 최대 힙이
같아야 하며, 중간값의 최대·최소 비율이 1.50을 넘으면 실패합니다. 현재 실행은
네 경로 모두 통과했고 가장 큰 비율은 1.316이었습니다.

이 검사는 눈에 띄는 내용 의존 동작을 잡기 위한 회귀 검사이며 상수 시간 인증이
아닙니다. FCH는 비키 해시이고 메시지는 공개된다고 가정합니다. 키를 쓰는 구성,
컴파일러가 만든 명령 차이, 캐시·분기 하드웨어 카운터, 전자기·전력 누설과 앞으로
나올 최적화 구현은 이 검사 범위에 포함되지 않습니다.

## 독립 검토 체크리스트

외부 검토는 정확한 커밋 하나를 대상으로 해야 합니다. 시작하기 전에 커밋 SHA,
플랫폼, 컴파일러와 도구 버전을 기록합니다. 대상이 바뀌면 변경된 부분을 다시
확인하기 전까지 기존 검토 결과는 기록된 커밋에만 적용됩니다.

이 체크리스트가 있고 저장소의 테스트를 통과했다는 사실만으로 독립 암호 검토가
끝난 것은 아닙니다. 설계에 참여하지 않은 검토자가 고정된 대상을 살펴보고 검토
범위, 방법, 발견 사항과 한계를 보고해야 완료된 것으로 볼 수 있습니다.

### 검토 순서

`fch_spec.ko.md`, `implementation_notes.ko.md`, 이 문서 순서로 읽은 뒤 각 주장을
구현과 테스트까지 따라가며 확인합니다.

| 영역 | 우선 확인할 파일 |
| ---- | ---------------- |
| 파라미터, 라운드, 상수와 압축 | `include/params.h`, `src/mix.c`, `src/bitops.c` |
| 역할별 레코드, 리프, 노드와 정규 분할 | `src/leaf.c`, `src/combine.c`, `src/fractal_split.c`, `src/fractal_process.c` |
| 공개 API, 출력 마무리와 스트리밍 | `src/fch.c`, `src/fch_stream.c`, `include/fch.h`, `include/fch_stream.h` |
| 기준 구현과 자동 탐색 | `tools/fch_reference.py`, `tools/fch_trail_search.py`, `tools/fch_characteristic_search.py`, `tests/` |

Python 기준 구현은 비교에 유용하지만 같은 저장소 안에서 함께 작성됐으므로 독립
사양은 아닙니다. C와 Python 결과가 같아도 양쪽에 같은 설계 오류가 남을 수
있습니다.

### 반드시 따져 볼 질문

1. **압축 코어:** 차분, 선형, 회전, 가산차분, rebound,
   meet-in-the-middle, 고정점, 불변 부분공간과 대칭 성질을 찾습니다. 결과가 전체
   16라운드인지 축소 라운드인지 구분하고, 8라운드 여유가 타당한지 평가합니다.
2. **인코딩:** 패딩과 모든 역할별 레코드가 단사인지 확인합니다. 역할, 자식 순서,
   레벨, 바이트·리프 범위, 원본 길이, 출력 크기와 마무리 정보가 혼동되거나
   빠질 수 없는지 검사합니다.
3. **트리 모드:** 충돌·제2원상 위치 논증, 구조 정보와 호환되는 표적 수,
   `T`와 `T_compatible` 계수를 검토합니다. 멀티콜리전, expandable message,
   herding, grafting, 장문, 다중 표적과 변형 간 재사용 공격도 확인합니다.
4. **출력:** feed-forward, 절단, FCH-256/FCH-512 분리와 출력 전 상태를 현재
   모델보다 싸게 노출하거나 재사용하는 경로가 있는지 살펴봅니다.
5. **구현:** 직렬화한 모든 필드를 사양과 대조합니다. 정수 한계, 할당 실패,
   소유권, aliasing, 정의되지 않은 동작, endian, 원샷·스트리밍 일치와 대용량
   입력 동작을 여러 컴파일러와 아키텍처에서 확인합니다.
6. **양자 범위:** 가역 오라클 가정, 한 번의 질의에 숨은 비용, 중첩 표적 판정,
   메모리 요구량과 구조적 양자 공격이 일반 블랙박스 기준선을 무효로 만드는지
   검토합니다.

기존 테스트가 통과했다는 이유만으로 질문을 닫으면 안 됩니다. 현재 검사 도구에
들어 있는 가정을 드러낼 수 있도록 입력군, 시드, 투영, 라운드 분할, 컴파일러와
플랫폼을 가능한 범위에서 바꿔 봐야 합니다.

### 근거와 보고 형식

암호분석 결과에는 정확한 함수와 공격 모델을 적고 시간, 데이터, 메모리와 쿼리
비용을 제시해야 합니다. 전체 라운드 결과와 축소 라운드 근거도 구분합니다. 구현
문제에는 가능한 한 작은 재현 입력, 사용한 명령과 환경, 예상 결과와 실제 결과를
포함합니다. 실제 공격을 만들지 못했더라도 논증에 근거가 없는 단계가 있다면 그
지점을 정확히 밝혀야 합니다.

발견 사항을 서로 비교하고 수정 후 다시 확인할 수 있도록 다음 항목을 사용합니다.

```text
ID:
제목:
대상 커밋:
심각도:
영향받는 주장:
파일 또는 함수:
모델과 가정:
재현 방법 또는 논증:
영향:
수정 제안:
상태:
```

| 심각도 | 이 프로젝트에서의 의미 |
| ------ | ----------------------- |
| Critical | 명시한 목표보다 훨씬 싼 재현 가능한 전체 라운드 공격이나 해시 결과를 무력화하는 악용 가능한 구현 결함 |
| High | 직접적인 보안 영향을 주는 신뢰할 만한 전체 라운드 지름길, 인코딩 모호성이나 구조 결함 |
| Medium | 주장한 여유를 바꾸는 중대한 축소 라운드 약점, 논증 공백이나 구현 불일치 |
| Low | 암호학적 붕괴가 확인되지 않은 하드닝, 이식성, 문서나 재현성 문제 |
| Informational | 현재 보안 영향이 없는 유용한 관찰, 부정 결과나 개선 제안 |

검토를 완료하려면 대상을 고정하고, 확인한 파일과 주장 목록을 남기며, 관련 테스트를
재현해야 합니다. 모든 발견 사항은 이유와 함께 open, fixed, accepted, rejected 중
하나로 정리하고 수정 사항을 다시 검사합니다. 최종 보고서에는 검토하지 않은 범위도
명시해야 합니다.

## 남은 분석

앞으로 우선해야 할 작업은 다음과 같습니다.

1. 고정된 커밋을 대상으로 위 독립 검토 체크리스트를 완료하고 검토 범위, 발견 사항,
   처리 결과와 해결되지 않은 한계를 공개
2. 실제 압축 구조에서 이상적 역할별 함수 모델로 이어지는 정식 환원, 적응형 질의의
   엄밀성, 구조 정보와 호환되는 목표 상태 수, 공격이 `T` 계수에 실제로 도달하는지 검토
3. 입력 범위와 구조화되지 않았거나 가중치가 더 큰 출력 마스크로 넓히고, 현재의
   두 고정 8비트 입력군을 넘어 일반적인 5~8라운드 특성을 찾는 MILP·SAT·SMT
   trail 자동 탐색
4. 현재의 제한된 전체 상태 단일 비트 characteristic 탐색을 선택된 고가중치 차분,
   solver 기반 탐색과 정량적 상한으로 확장하고, rebound·meet-in-the-middle
   검사를 최적화된 inbound와 독립 neutral variable로 확대하며 출력 전용 탐색도
   고정된 16비트 입력군보다 넓은 범위로 확장
5. 멀티콜리전, expandable message, herding, 다중 표적과 변형 간 재사용에 대해
   실제 공격을 구성하거나 더 엄밀한 한계를 구하고 위 합집합 상한의 정확도 확인
6. 장시간 외부 퍼징, 하드웨어 카운터 기반 실행 시간 분석과 앞으로 나올 최적화
   구현의 부채널 평가
7. 가역 회로의 게이트·깊이·큐비트·보조 큐비트 추정, 메모리를 고려한 충돌 공격의
   절충 분석, 압축 코어와 트리 모드에 대한 양자 구조 공격, 양자 랜덤 오라클
   모델에서의 증명이나 환원

현재 탐색에서 공격을 찾지 못한 결과는 이 작업들의 출발점으로 봐야 하며,
더 강한 공격이 없다는 뜻으로 해석하면 안 됩니다.

## 결과 재현

`build` 디렉터리에서 실행합니다.

```sh
make clean
make check
make check-extended
make check-reference
make check-trails
make check-characteristics
make bench-check
make timing-check
make fuzz-smoke
make analyze
```

`test_cryptanalysis`와 `test_tree_attacks`는 표본 수와 측정값을 직접 출력합니다.
의사난수 입력에 고정된 시드를 사용하므로 같은 소스와 파라미터에서는 같은
분석 결과를 얻을 수 있습니다.
