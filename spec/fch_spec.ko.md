# Fractal Crypt-Hash 사양(Specification)

## 0. 범위 및 비목표(Scope & Non-Goals)

이 문서는 FCH 레퍼런스 설계의 **결정적 동작(behavior)** 을 정의하기 위한 사양입니다.
충돌 저항/원상 저항 등 **암호학적 안전성**을 보장하거나 주장하지 않습니다.
따라서 실전 보안 목적의 프로덕션 사용 근거로 삼지 마세요.

FCH는 연구, 실험, 벤치마크, 토론 목적을 권장합니다.

---

## 1. 보안 목표 및 현재 상태(Security Targets and Status)

### 1.1 공격자 모델

FCH는 공개된 결정적 비키 해시 함수입니다. 공격자는 알고리즘, 상수,
메시지와 해시 결과를 알 수 있고 해시할 메시지를 자유롭게 선택할 수 있다고
가정합니다. 아래 목표는 고전적 계산 모델만을 대상으로 하며 양자 공격에 대한
보안 강도는 현재 정의하거나 주장하지 않습니다.

### 1.2 목표 강도

| 변형 | 출력 크기 | 충돌 저항 | 원상 저항 | 제2원상 저항 |
| ---- | --------- | --------- | --------- | ------------- |
| FCH-256 | 256 bits | 2^128 | 2^256 | 2^256 |
| FCH-512 | 512 bits | 2^256 | 2^512 | 2^512 |

각 수치는 이상적인 해당 출력 크기 해시에서 기대하는 대략적인 일반 공격 비용을
의미합니다. 이는 FCH가 반드시 달성해야 할 **설계 목표**이지, 현재 설계가
그 강도를 달성했다는 보안 주장이나 증명이 아닙니다. 구조적 약점이 발견되면
실제 보안 강도는 이 목표보다 낮아질 수 있습니다.

### 1.3 구조적 보안 목표

FCH의 트리 구조는 다음을 목표로 합니다.

- 루트, 내부 노드, 리프, 자식 상태를 서로 다른 영역으로 분리
- 노드 종류, 깊이, 길이, 자식 수, 자식 순서, 오프셋과 길이를 모호하지 않게 반영
- 서로 다른 메시지 또는 트리 구조가 같은 내부 표현으로 합쳐지는 구조적 충돌 방지
- 멀티충돌, herding, 긴 메시지 제2원상 공격 등 트리 해시 특화 지름길이
  목표 강도보다 낮아지지 않도록 설계
- 원샷 및 스트리밍 API가 입력 방식과 관계없이 같은 메시지에 같은 출력을 생성

### 1.4 보안 후보 판정 기준

FCH를 실전 검토가 가능한 보안 후보로 평가하려면 최소한 다음 근거가 필요합니다.

- 구현과 일치하는 안정적이고 완전한 사양
- 전체 설계와 축소형에 대한 차분, 선형, 구조적 공격 분석
- 공격 결과와 비교할 수 있는 명시적인 보안 여유
- 표의 목표 비용보다 빠른 알려진 전체 설계 공격의 부재
- 재현 가능한 시험 결과와 의미 있는 독립 공개 검토

통계적 분포, avalanche, 테스트 벡터 및 구현 테스트는 분석을 돕는 자료이지만
그 자체로 암호학적 안전성을 입증하지 않습니다.

---

## 2. 입력 패딩(Input Padding)

길이가 L 바이트인 입력 메시지 M에 대해:

1. 바이트 0x80을 추가
2. 0x00 바이트들을 추가
3. (L × 8)의 64-bit little-endian 값을 추가
4. 전체 길이가 FCH_MIN_BLOCK_SIZE 이상이 되도록 보장

64비트 비트 길이 필드로 안전하게 표현할 수 없는 입력 길이는
checked API에서 거부합니다.

---

## 3. 프랙탈 처리(Fractal Processing)

처리는 depth = 0에서 시작합니다.

각 노드에서:

- depth ≥ MAX_DEPTH 또는 length ≤ MIN_BLOCK_SIZE 이면:
  → 리프(leaf) 압축
- 그 외의 경우:
  → 가변 n-way 분할 후 재귀 처리

---

## 4. 가변 n-Way 분할(Variable n-Way Split)

- n ∈ [2, 6]
- 64-bit 분할 시드에 노드 길이, 깊이, 모든 입력 바이트를 반영
- 혼합된 시드에서 n과 각 분할 가중치를 유도
- 블록은 전체 입력을 겹치지 않게 완전히 덮음

---

## 5. 리프 압축(Leaf Compression)

리프 노드는 다음을 적용합니다:

- XOR
- ADD
- ROTATE
- 8×8 S-box 치환
- 네 번의 상태 간 최종 혼합

모든 64비트 회전 횟수는 64로 나눈 나머지로 정의합니다.
S-box 치환은 호스트 바이트 순서와 관계없이 최하위 바이트부터 적용합니다.

처리 후:

- 루트 리프와 내부 리프에 서로 다른 영역 상수 사용
- 길이, 깊이, 상태 폭을 상태에 혼합
- 상위 노드까지 전체 상태 폭을 유지

---

## 6. 트리 결합 및 재압축(Tree Combine & Recompression)

내부 노드는:

- 자식 상태를 순차적으로 병합(순서 의존)
- 노드 길이, 깊이, 자식 수, 상태 폭을 혼합
- 각 자식의 순서, 오프셋, 길이를 혼합
- 산술 혼합 및 회전 적용
- S-box 치환 적용
- 전체 상태 폭을 유지

---

## 7. 출력(Output)

- 루트 상태를 little-endian 바이트로 직렬화
- FCH-256: 32 bytes
- FCH-512: 64 bytes

메모리 할당 또는 검증 실패 시 다른 트리 계산으로 대체하지 않습니다.
checked API는 실패를 반환하고 출력 버퍼를 0으로 지웁니다.

---

## 8. 스트리밍 처리(Streaming Processing)

- update 호출은 입력 바이트를 익명 임시 저장소에 기록
- final 단계는 저장된 입력과 가상 패딩을 임의 접근 리더로 제공
- 리더는 원샷 입력과 같은 분할, 리프, 결합 규칙을 적용
- RAM 사용량은 고정 크기 입출력 버퍼와 재귀 상태로 제한
- final 단계에서 임시 저장소를 닫음
- final 이후의 update와 final 재호출은 실패

따라서 스트리밍은 원샷과 같은 해시를 유지하지만 임시 파일 지원이 필요하고
입출력 횟수가 늘어날 수 있습니다.
