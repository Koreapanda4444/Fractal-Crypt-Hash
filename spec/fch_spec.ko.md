# Fractal Crypt-Hash 사양(Specification)

## 0. 범위 및 비목표(Scope & Non-Goals)

이 문서는 FCH 레퍼런스 설계의 **결정적 동작(behavior)** 을 정의하기 위한 사양입니다.
충돌 저항/원상 저항 등 **암호학적 안전성**을 보장하거나 주장하지 않습니다.
따라서 실전 보안 목적의 프로덕션 사용 근거로 삼지 마세요.

FCH는 연구, 실험, 벤치마크, 토론 목적을 권장합니다.

---

## 1. 보안 목표 및 현재 상태(Security Targets and Status)

### 1.1 공격자 모델

FCH는 공개된 결정적 비키 해시 함수입니다. 공격자는 알고리즘, 상수,
메시지와 해시 결과를 알 수 있고 해시할 메시지를 자유롭게 선택할 수 있다고
가정합니다. 아래 목표는 고전적 계산 모델만을 대상으로 하며 양자 공격에 대한
보안 강도는 현재 정의하거나 주장하지 않습니다.

### 1.2 목표 강도

| 변형 | 출력 크기 | 충돌 저항 | 원상 저항 | 제2원상 저항 |
| ---- | --------- | --------- | --------- | ------------- |
| FCH-256 | 256 bits | 2^128 | 2^256 | 2^256 |
| FCH-512 | 512 bits | 2^256 | 2^512 | 2^512 |

각 수치는 이상적인 해당 출력 크기 해시에서 기대하는 대략적인 일반 공격 비용을
의미합니다. 이는 FCH가 반드시 달성해야 할 **설계 목표**이지, 현재 설계가
그 강도를 달성했다는 보안 주장이나 증명이 아닙니다. 구조적 약점이 발견되면
실제 보안 강도는 이 목표보다 낮아질 수 있습니다.

### 1.3 구조적 보안 목표

FCH의 트리 구조는 다음을 목표로 합니다.

- 루트, 내부 노드, 리프, 자식 상태를 서로 다른 영역으로 분리
- 노드 종류, 깊이, 길이, 자식 수, 자식 순서, 오프셋과 길이를 모호하지 않게 반영
- 서로 다른 메시지 또는 트리 구조가 같은 내부 표현으로 합쳐지는 구조적 충돌 방지
- 멀티충돌, herding, 긴 메시지 제2원상 공격 등 트리 해시 특화 지름길이
  목표 강도보다 낮아지지 않도록 설계
- 원샷 및 스트리밍 API가 입력 방식과 관계없이 같은 메시지에 같은 출력을 생성

### 1.4 보안 후보 판정 기준

FCH를 실전 검토가 가능한 보안 후보로 평가하려면 최소한 다음 근거가 필요합니다.

- 구현과 일치하는 안정적이고 완전한 사양
- 전체 설계와 축소형에 대한 차분, 선형, 구조적 공격 분석
- 공격 결과와 비교할 수 있는 명시적인 보안 여유
- 표의 목표 비용보다 빠른 알려진 전체 설계 공격의 부재
- 재현 가능한 시험 결과와 의미 있는 독립 공개 검토

통계적 분포, avalanche, 테스트 벡터 및 구현 테스트는 분석을 돕는 자료이지만
그 자체로 암호학적 안전성을 입증하지 않습니다.

### 1.5 라운드 정책과 현재 여유 상태

실제 FCH 해시는 항상 16라운드를 사용합니다. 레퍼런스 구현은 코어의 단일 비트
확산을 4·8·12·16라운드에서 측정하며, 보수적으로 8라운드를 축소형 비교
기준으로 사용합니다. 따라서 정식 설계는 이 기준보다 8라운드 높습니다.

이는 **운용상 라운드 간격**이지 암호학적으로 증명된 보안 여유가 아닙니다.
레퍼런스 테스트는 1·2·4·8·16라운드의 제한된 선택 차분 탐색,
8·16라운드의 차분 비트 편향 및 선형 상관 검사, 고정점·2주기·충돌·근접
충돌 탐색을 수행합니다. 이 결정적 CI 검사는 정해진 표본 범위 안의 단순한
성질만 걸러냅니다. 일반적인 차분·선형·회전·rebound·구조 공격 저항을
측정하지 않으므로, 실제 보안 여유를 주장하려면 축소 라운드와 전체 설계에
대한 공격 기반 분석이 추가로 필요합니다.

## 2. 입력 패딩(Input Padding)

길이가 L 바이트인 입력 메시지 M에 대해:

1. 바이트 0x80을 추가
2. 0x00 바이트들을 추가
3. (L × 8)의 64-bit little-endian 값을 추가
4. 전체 길이가 FCH_MIN_BLOCK_SIZE 이상이 되도록 보장

64비트 비트 길이 필드로 안전하게 표현할 수 없는 입력 길이는
checked API에서 거부합니다.

---

## 3. 프랙탈 처리(Fractal Processing)

처리는 depth = 0에서 시작합니다.
음수 depth와 8워드가 아닌 내부 상태 폭은 유효한 트리 표현이 아니므로
거부합니다.

각 노드에서:

- depth ≥ MAX_DEPTH 또는 length ≤ MIN_BLOCK_SIZE 이면:
  → 리프(leaf) 압축
- 그 외의 경우:
  → 가변 n-way 분할 후 재귀 처리

---

## 4. 가변 n-Way 분할(Variable n-Way Split)

- n ∈ [2, 6]
- 블록은 전체 입력을 겹치지 않게 완전히 덮음
- 내부 노드의 자식 블록은 offset 0부터 빈틈없이 이어지고 길이는 모두 1 이상

각 내부 노드에서 FCH는 동일한 ARX 코어와 분할 전용 `FCHSPLT1` 영역을
사용해 512비트 분할 파생값을 만듭니다. 먼저 분할 파생 버전 1의 고정
128바이트 `FCHSPH01` 헤더를 압축합니다. 이 헤더에는 노드 길이와 깊이,
내부 상태 폭, 분기 수 범위, 분할 가중치 범위, 최소 블록 크기, 최대 깊이,
압축 블록 크기, 라운드 수와 트리 인코딩 버전을 반영합니다.

그 뒤 노드의 전체 입력을 8바이트 `FCHSPD01` 태그와 최대 120바이트의
원본 데이터로 구성된 레코드들에 넣어 흡수합니다. 실제 레코드 길이,
누적 바이트 수와 마지막 레코드 여부는 압축 tweak에 반영합니다.
마지막으로 고정 `FCHSPO01` 출력 레코드에 같은 설정, 입력 레코드 수와
추출 횟수 카운터를 반영합니다.

`r = N_MAX - N_MIN + 1`, `t = (2^64 mod r)`라고 할 때 첫 번째 파생
워드가 `t` 이상인 경우에만 사용합니다. 그렇지 않으면 영역이 분리된
출력 추출을 한 번 더 수행합니다. 자식 수는 다음과 같습니다.

`n = N_MIN + (material[0] mod r)`

길이가 `2 × MIN_BLOCK_SIZE`보다 짧은 내부 노드는 모든 지원 분기 설정에서
정규 구조를 유지하도록 `n = N_MIN`을 사용합니다. 그 밖의 내부 노드는 위
공식을 사용합니다. rejection sampling은 나머지 연산의 편향을 없앱니다.
각 자식 `i`의 가중치는 다음과 같습니다.

`weight[i] = 128 + (material[i + 1] AND 0x7f)`

따라서 가중치는 `[128, 255]` 범위이며, 하나의 내부 노드가 극단적으로
한쪽에 몰리는 것을 제한합니다. 길이 배분은 각 자식에 최소 1바이트를
보장하고 반올림 나머지를 마지막 자식에 배정합니다.

FCH는 공개된 결정적 비키 해시이므로 공격자가 여러 메시지를 탐색해 원하는
`n`을 찾는 행위 자체까지 막을 수는 없습니다. 이 파생 구조의 목적은 기존
64비트 누산값에 대한 값싼 국소·대수적 조작 경로를 제거하고 병적인 불균형을
제한하는 것이며, 비밀 또는 키 기반 분할 함수로 취급하지 않습니다.

## 5. 리프 압축(Leaf Compression)

FCH-256과 FCH-512는 모두 8개의 64비트 워드로 이루어진 512비트 내부
트리 상태를 사용합니다. 리프 노드는 루트 리프와 내부 리프에 서로 다른
영역 상수를 사용해 상태를 초기화합니다.

먼저 `FCHLEAF1` 형식 태그와 인코딩 버전 1을 포함하는 128바이트 리프
헤더를 압축합니다. 헤더에는 영역, 리프 길이, 깊이, 상태 폭, 최소 블록 크기,
최대 깊이, 분기 수 범위, 압축 블록 크기, 라운드 수, 분할 가중치 범위와
분할 파생 버전을 고정 위치의 64비트 little-endian 필드로 기록합니다.
사용하지 않는 필드는 0입니다.

리프 데이터 레코드는 `FCHLDAT1` 8바이트 태그 뒤에 최대 120바이트의 원본
데이터를 둡니다. 마지막 부분 레코드의 나머지는 0이며, 레코드의 실제 길이와
누적 원본 바이트 수를 각각 block-length tweak와 counter에 반영합니다.
빈 리프도 태그만 포함한 하나의 final 데이터 레코드를 처리합니다.
마지막 데이터 레코드에는 final 플래그를 설정합니다.

### 5.1 정규 레코드 규칙

- 모든 형식 태그는 정확히 8바이트 ASCII입니다.
- 모든 숫자 필드는 부호 없는 64비트 little-endian입니다.
- 형식 버전은 1이며 형식 변경 시 버전과 고정 테스트 벡터가 함께 변경됩니다.
- 리프 헤더, 노드 헤더, 자식 레코드, 출력 헤더, 분할 헤더와 분할 출력
  레코드는 각각 128바이트입니다. 태그가 붙는 리프·분할 데이터 레코드는
  8~128바이트의 실제 길이를 사용합니다.
- 레코드 종류마다 서로 다른 태그, 압축 플래그와 영역 상수를 사용합니다.
- 음수 깊이, 2개 미만 또는 6개 초과의 자식, 빈 자식, 겹침·빈틈·범위 초과
  분할은 거부합니다.

### 5.2 ARX 압축 코어

각 압축은 16개의 64비트 워드로 이루어진 작업 상태를 사용합니다.
앞 8개 워드는 현재 체이닝 상태, 뒤 8개 워드는 고정 IV로 초기화합니다.
카운터, 실제 블록 길이, 상태 폭, 영역 상수와 플래그를 작업 상태에 XOR한 뒤
16라운드를 수행합니다. 각 라운드는 열 방향 G 함수 네 번과 대각선 방향
G 함수 네 번으로 모든 작업 워드를 섞습니다.

G 함수는 64비트 모듈러 덧셈, XOR, 오른쪽 회전만 사용하며 다음 순서로
정의합니다.

1. `a = a + b + x`, `d = ROTR64(d XOR a, 32)`
2. `c = c + d`, `b = ROTR64(b XOR c, 24)`
3. `a = a + b + y`, `d = ROTR64(d XOR a, 16)`
4. `c = c + d`, `b = ROTR64(b XOR c, 63)`

메시지 스케줄은 고정 순열 10개를 순환해 사용합니다. 0~9라운드는 10개
순열을 순서대로 사용하고 10~15라운드는 0~5번 순열을 다시 사용합니다.

16라운드 후 각 체이닝 워드 `h[i]`는
`h[i] XOR work[i] XOR work[i + 8]`로 갱신됩니다.
G 함수의 형태와 회전값은 BLAKE2b의 64비트 ARX 구조를 따르지만,
FCH의 초기화, tweak, 메시지 처리와 트리 모드는 별도 설계입니다.
따라서 BLAKE2b의 보안성을 FCH가 그대로 이어받는다고 주장하지 않습니다.

## 6. 트리 결합 및 재압축(Tree Combine & Recompression)

내부 노드는:

- 루트 노드와 일반 내부 노드에 서로 다른 영역 상수를 사용
- `FCHNODE1` 태그와 버전 1의 노드 헤더를 먼저 압축
- 노드 헤더에 분할 가중치 범위와 분할 파생 버전을 반영
- 각 자식을 아래의 `FCHCHLD1` 128바이트 레코드로 직렬화
- 자식 블록을 순서대로 16라운드 ARX 코어에 입력
- 마지막 자식 블록에 final 플래그를 설정
- 결합 후에도 512비트 전체 상태를 유지

| 64비트 워드 | 자식 레코드 필드 |
| ----------- | ---------------- |
| 0 | `FCHCHLD1` |
| 1 | 인코딩 버전 |
| 2 | 부모 노드 길이 |
| 3 | 부모 깊이 |
| 4 | 전체 자식 수 |
| 5 | 자식 순서 |
| 6 | 부모 안에서의 자식 오프셋 |
| 7 | 자식 길이 |
| 8–15 | 512비트 자식 상태 |

## 7. 출력(Output)

- `FCHOUT01` 태그, 인코딩 버전, 출력 폭, 내부 상태 폭, 블록 크기와
  라운드 수를 담은 고정 출력 헤더로 루트 상태를 한 번 더 압축
- FCH-256과 FCH-512에 서로 다른 출력 영역 상수 사용
- FCH-256은 최종 512비트 상태의 앞 4개 워드를 little-endian으로 직렬화
- FCH-512는 최종 상태의 8개 워드를 모두 little-endian으로 직렬화
- 결과 크기: FCH-256은 32 bytes, FCH-512는 64 bytes

메모리 할당 또는 검증 실패 시 다른 트리 계산으로 대체하지 않습니다.
checked API는 실패를 반환하고 출력 버퍼를 0으로 지웁니다.

---

## 8. 스트리밍 처리(Streaming Processing)

- update 호출은 입력 바이트를 익명 임시 저장소에 기록
- final 단계는 저장된 입력과 가상 패딩을 임의 접근 리더로 제공
- 리더는 원샷 입력과 같은 분할, 리프, 결합 규칙을 적용
- RAM 사용량은 고정 크기 입출력 버퍼와 재귀 상태로 제한
- final 단계에서 임시 저장소를 닫음
- final 이후의 update와 final 재호출은 실패

따라서 스트리밍은 원샷과 같은 해시를 유지하지만 임시 파일 지원이 필요하고
입출력 횟수가 늘어날 수 있습니다.

---

## 9. 트리 공격 분석 상태(Tree Attack Analysis Status)

트리 인코딩은 유효한 자식 상태가 다른 구조적 문맥에 조용히 재사용되는 것을
막기 위해 다음 정보를 결합합니다:

- 리프 헤더: 리프 길이와 깊이
- 노드 헤더: 부모 길이, 깊이, 자식 수 및 설정
- 자식 레코드: 순서, 오프셋, 길이, 부모 메타데이터 및 자식 상태
- 루트·내부 노드·리프·분할·출력에 서로 다른 영역
- 부모 입력 전체를 읽는 내용 의존 분할 파생

현재 공격별 상태는 다음과 같습니다:

| 공격 종류 | 현재 자동 검사 | 남아 있는 한계 |
| --------- | -------------- | -------------- |
| 멀티콜리전 | 리프 상태 4,096개와 파생 노드 상태 4,096개의 전체 충돌 및 20비트 접두부 버킷 이상 검사 | 작은 축약 검사는 512비트 내부 충돌 비용을 입증하거나 Joux형 구성을 배제하지 못함 |
| 제2원상 | 16 KiB 표적에 대해 비트 변경·청크 교체·교환·splice 후보 512개 검사 | expandable message·herding 등 전용 공격에 대한 FCH-256/512 목표 비용을 입증하지 못함 |
| 트리 모양/상태 이식 | 동일한 자식 상태를 이진·평면·비대칭·역순·경계 변경·깊이 변경 문맥에서 재결합 | 구조 결합의 안전성은 여전히 압축 코어의 충돌 및 선택 상태 공격 저항에 의존 |
| 장문 메시지 | append·truncate·prefix·패딩 삽입 extension·청크 교환/복사/회전·경계 변경·저엔트로피 패턴을 포함한 256 KiB 변형 15개 검사 | 더 큰 탐색, 적대적 분할 조절, 깊이 제한 리프 및 자원 고갈 분석이 남음 |

멀티콜리전 검사의 20비트 접두부는 CI 안에서 일반적인 birthday collision이
실제로 나타날 정도로 의도적으로 작습니다. 이 테스트는 비정상적인 버킷 집중과
512비트 전체 상태의 동일 여부를 검사할 뿐, 전체 상태 안전성의 증명이 아닙니다.

분할 파생은 각 노드에서 모든 바이트를 읽은 다음 자식을 재귀 처리합니다.
입력 길이를 `L`, 실제 트리 깊이를 `d`라고 하면 입력 읽기 작업량은
`O(L * d)`이며 `d`는 16으로 제한됩니다. 원샷 해시는 패딩에 `O(L)` 메모리를
추가로 사용합니다. 스트리밍은 RAM을 제한하지만 `O(L)` 임시 저장공간을 쓰고
트리 단계마다 I/O가 반복될 수 있습니다. 따라서 암호학적 공격이 발견되지
않더라도 대용량 입력에 의한 CPU·디스크·임시파일 고갈은 구현 위험입니다.

현재 제한된 표본에서는 단순 구조 alias, 전체 상태 충돌 또는 제2원상이
발견되지 않았습니다. 이 결과는 FCH의 실험적 상태를 바꾸거나 독립적인
트리 해시 암호분석을 대신하지 않습니다.
