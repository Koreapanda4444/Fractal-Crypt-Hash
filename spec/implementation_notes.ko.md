# 구현 노트

이 문서는 C 레퍼런스 구현에서 선택한 방식과 제약을 정리합니다. 알고리즘의
정확한 정의는 [fch_spec.ko.md](fch_spec.ko.md)에 있습니다.

## 구성

FCH의 확산은 두 층으로 이루어집니다. 16라운드 ARX 코어가 한 번의 압축
안에서 데이터를 섞고, 재귀 트리가 리프의 변화를 부모 노드와 루트까지
전달합니다. 트리는 코어를 대체하는 장치가 아니라 코어 바깥에 더해지는
구조입니다.

두 출력 변형은 같은 8워드 내부 상태를 사용합니다. 리프, 내부 노드, 분할
파생과 출력 마무리는 서로 다른 영역과 레코드를 사용합니다. 자식 레코드에는
순서, 오프셋, 길이, 부모 정보와 512비트 자식 상태 전체가 들어갑니다.

## 이식성

구현은 호스트의 바이트 순서에 의존하지 않도록 작성했습니다.

- 상태 워드는 `uint64_t`를 사용합니다.
- 모듈러 덧셈은 C의 부호 없는 정수 연산을 따릅니다.
- 회전 횟수는 64로 나눈 나머지로 처리합니다.
- 패딩, 메타데이터와 출력은 명시적인 little-endian load/store를 사용합니다.
- 구조 정보는 고정된 64비트 필드에 기록합니다.
- 분할 계산은 크기를 더하거나 곱하기 전에 overflow를 검사합니다.

현재 CI는 x86-64 Linux·macOS·Windows를 다룹니다. 다음 이식성 작업에서는
직렬화 테스트만으로 판단하지 않고 32비트와 big-endian 환경을 직접 실행할
예정입니다.

## 오류 처리

checked 원샷·스트리밍 API는 성공 여부를 반환합니다. 잘못된 포인터,
지원하지 않는 길이, 메모리 할당 실패, 리더 오류와 비정규 트리 배치는
호출자까지 전달됩니다. 처리에 실패했을 때 다른 트리로 대신 계산하거나
부분 상태를 결과로 사용하지 않습니다.

실패 시 공개 출력 버퍼를 0으로 지웁니다. 실패한 스트리밍 컨텍스트는 free
전까지 실패 상태를 유지하고, final을 다시 호출하면 출력 버퍼를 지운 뒤
실패합니다. 활성 컨텍스트는 하나의 호출 흐름에서만 소유해야 하며 복사하거나
동시에 사용하면 안 됩니다.

## 스트리밍 경로

update는 입력을 익명 임시 파일에 이어 씁니다. final 단계에서는 이 파일을
트리 처리용 임의 접근 리더로 제공하고, 완성된 패딩 전체를 RAM에 올리지 않고
필요한 구간만 만들어 냅니다.

따라서 애플리케이션 메모리는 제한되지만 한 번만 읽는 온라인 트리 해시는
아닙니다. 분할 파생이 방문한 노드의 전체 내용을 읽기 때문에 같은 메시지
구간을 여러 깊이에서 다시 읽을 수 있습니다. 임시 저장공간은 메시지 길이에
비례하며 디스크 I/O도 스트리밍 비용에 포함됩니다.

## 분할 구현

분할 파생값은 노드 전체 입력과 전용 영역으로 계산합니다. 분기 수는 rejection
sampling으로 뽑고, 나머지 상태 워드에서 128~255 범위의 가중치를 가져옵니다.
비례 배분이 끝나면 각 자식이 1바이트 이상이고, 연속되고, 겹치지 않으며,
부모 전체를 정확히 덮도록 길이를 보정합니다.

이 방식은 국소 변화로 조절하기 쉬웠던 이전 64비트 누산값을 대체했습니다.
현재 분할도 공개된 결정적 함수이며, 목적은 비밀 분할이 아니라 전체 입력과
트리 구조를 결합하는 데 있습니다.

## 확정된 다음 트리 형식

다음 비호환 트리 형식은 사양서 12절에 정의했습니다. 1,024바이트 고정 리프와
왼쪽의 완전 서브트리를 우선하는 이진 트리를 사용합니다. 리프와 노드 구조에는
절대 바이트 범위, 리프 범위와 레벨이 들어갑니다. 메시지 바이트로 분기 수, 가중치나
경계를 고르지 않습니다.

이번 결정은 문서에만 반영되며 현재 구현의 결과를 바꾸지 않습니다. 다음
항목이 모두 버전 2로 함께 전환될 때까지 버전 1이 계속 유효합니다.

- C 원샷 및 스트리밍 경로
- Python 레퍼런스
- 레코드 태그, 영역과 구조 검증
- 예상 해시 결과와 트리 인코딩 테스트
- 사양서의 규범 파라미터와 처리 절

부분 호환 모드는 추가하지 않습니다. 버전 2 구현은 지원하지 않는 구조나
메모리 할당 실패가 발생했을 때 버전 1 결과로 대신 계산하면 안 됩니다.

구현에서는 완성된 2의 거듭제곱 크기 서브트리를 스택에 보관합니다. 일반
update는 최종 메시지 길이를 몰라도 가득 찬 리프를 확정할 수 있습니다.
final은 남은 부분 리프와 패딩을 처리하고 스택을 오른쪽부터 결합한 뒤,
`FCHOUT02`에서 전체 범위를 결합합니다. 앞에서 처리한 리프를 다시 읽을 필요가
없으며, 이후 임시 파일 기반 스트리밍을 교체할 수 있는 기반이 됩니다.

## 분석 훅과 테스트

축소 라운드 압축은 분석용 타깃에서만 컴파일합니다. 디버그 훅은 컴파일러별
weak symbol 대신 명시적인 외부 훅 설정을 사용합니다. 일반 빌드는 항상
16라운드를 실행합니다.

테스트는 고정 출력, 경계값, 트리 불변성, 영역 분리, 분할 민감도, 축소 라운드
확산, 제한된 암호분석 탐색, 트리 공격 패턴, API 오용, 리더 실패와 원샷/
스트리밍 동일성을 다룹니다. sanitizer와 libFuzzer 스모크 작업도 일반
테스트와 같은 구현 경로를 실행합니다.

## 최적화 원칙

최적화보다 해시 결과의 호환성을 우선합니다. 메모리 할당, 버퍼링, 파일 탐색과
작업 순서를 바꿀 때는 고정 출력과 원샷/스트리밍 동일성을 유지해야 합니다.
영역, 태그, 필드 배치, 라운드 수, 분기 수, 가중치나 깊이 제한을 바꾸는 작업은
구현 최적화가 아니라 알고리즘 변경으로 취급합니다.
